# 项目整体汇报大纲

## 1. 文档用途
这份文档用于给做 PPT / 演示视频 / 答辩汇报的同学提供一份完整的讲述框架。

它不是逐字稿，而是整套汇报的主线、页序、每页重点和讲述口径。

当前建议按以下结构组织整场汇报：
- `goal`
- `如何形成产品`
- `基本功能`
- `广告`
- `技术：算法第 1 页`
- `技术：算法第 2 页`
- `Xcode 版本`
- `demo 展示`
- `crossover`

---

## 2. 一句话总主线
《拍立食》不是传统菜谱 App，也不是完整电商平台，而是一个最终落地到微信小程序的“剩余食材重构体验”产品。

用户把手边已有食材拍下来，系统先识别食材，再在约束条件下生成一道高完成度的菜品方案，并把结果保存进个人档案；同时通过社区展示和 Shop 导购壳，把“创作感、分享感、可执行性”串成一个完整产品故事。

---

## 3. 建议页序与每页内容

### 第 1 页：封面
建议标题：
- 《拍立食》项目汇报

副标题可写：
- 面向剩余食材重构的微信小程序产品方案

这一页只做开场，不讲太满，作用是把项目一句话说清楚。

---

### 第 2 页：goal
这一页回答两个问题：
- 我们为什么要做这个产品
- 这个产品到底想解决什么问题

建议讲法：
- 很多人家里经常会剩下一些零散食材，但不知道能做什么。
- 传统菜谱 App 更偏向“搜索某道菜怎么做”，但不能很好解决“我现在手头只有这些食材，接下来怎么办”。
- 所以《拍立食》要解决的是：把零散、随机、低确定性的剩余食材，变成一个可识别、可生成、可保存、可分享的产品体验。

这一页结论建议落在：
- 降低做饭决策成本
- 提升剩余食材利用率
- 把做菜从功能行为变成更有趣的创作体验

一句话收尾可以讲：
- 我们不是帮用户查一道标准菜谱，而是帮用户把眼前现有食材重组为一道值得做的菜。

---

### 第 3 页：如何形成产品
这一页讲“产品是怎么被收敛出来的”，而不是直接讲技术。

建议讲法：
- 我们不是先从炫技或大模型出发，而是先从用户问题出发。
- 之后把需求收敛成三层：
  - 主链路：拍摄识别 -> 确认 -> 生成 -> 结果 -> 保存
  - 资产层：档案馆，沉淀用户历史作品
  - 展示支线：社区展示 + Shop 导购壳
- 当前先用 H5 原型把页面结构、交互顺序和主链路跑顺。
- 最终正式落地形态统一为微信小程序，而不是 Web App。

这一页重点要说明：
- 我们不是一开始就做一个大而全的平台
- 而是先把最核心、最可展示、最可落地的 MVP 定义清楚

可以直接点出当前主链路：
- 微信登录
- 首页 Nexus
- 拍摄识别
- 分子重构确认
- 加载过渡
- 结果页
- 保存归档
- 档案馆

---

### 第 4 页：基本功能
这一页讲产品“现在到底能做什么”。

建议分成 4 块来讲：

1. 主链路
- 用户登录后进入 Nexus
- 从 Nexus 进入拍摄
- 拍摄后完成食材识别和确认
- 进入加载和生成
- 得到结果页
- 保存进入档案馆

2. 档案馆
- 保存用户生成过的作品
- 支持回看和展示

3. 社区
- 目前只做展示，不做真实社区后端
- 作用是让用户看到别人分享的内容，形成“种草”

4. Shop
- 从社区内容进入第三方平台入口
- 当前只做导购壳，不做交易闭环

这一页的讲法一定要稳：
- 社区只做展示
- Shop 只做导购入口
- 当前优先保证主链路完整

---

### 第 5 页：广告
这一页建议讲成“未来商业化和品牌合作入口”，不要讲成“现在已经做了广告系统”。

建议讲法：
- 当前版本不做复杂广告系统，也不做真实电商闭环。
- 但产品天然具备商业化延展空间。
- 社区内容、结果页和 Shop 入口都可以承接未来的品牌合作和导流。

可以举的方向：
- 食材平台导流
- 厨具品牌合作
- 健康饮食内容联动
- 节日主题活动页
- 联名挑战或推荐专区

这一页的价值在于：
- 不夸大当前实现
- 但能说明产品不只是课程作业，也具备延展性

---

### 第 6 页：技术 / 算法第 1 页
这一页建议讲“整体技术结构”。

推荐标题：
- 技术架构：从原型到正式落地

一句话架构：
- `微信小程序前端 -> 单体后端 API -> 数据库 + 对象存储 -> 识别/生成能力`

建议讲法：
- H5 原型负责统一页面结构、交互逻辑和视觉基线
- 小程序前端负责正式产品页面和用户交互
- 后端负责登录、上传、识别、生成、归档、社区读取和 Shop 配置
- 数据库负责用户、档案馆、社区内容、健康规则等结构化数据
- 对象存储负责拍摄图、生成图和卡片图

这一页的重点不是技术细节，而是让老师知道：
- 我们有明确的技术分层
- H5 只是原型，不是最终技术栈
- 最终是可以落到正式工程里的

---

### 第 7 页：技术 / 算法第 2 页
这一页讲“算法在项目里到底起什么作用”。

推荐标题：
- 约束式大模型生成：从剩余食材到高完成度菜品

这一页建议重点讲下面 5 步：

1. 食材识别
- 先识别用户拍到的食材
- 把图像输入转成结构化输入
- 包括食材名称、数量、可用性、主辅关系等

2. 约束提取
- 系统不会无限生成，而是先确定约束条件
- 包括：
  - 用户当前真实拥有的食材
  - 可补充的基础调料
  - 可用厨具
  - 技法偏好
  - 味觉偏好
  - 时间成本
  - 食安和过敏规则

3. 菜品结构规划
- 先决定这道菜的骨架，而不是直接输出整段文案
- 包括：
  - 主体食材是谁
  - 核心技法是什么
  - 风味基调是什么
  - 谁负责口感层次
  - 谁负责香气和摆盘表达

4. 大模型生成
- 在约束条件和菜品骨架下，让大模型生成：
  - 菜名
  - 成品描述
  - 做法步骤
  - 风味说明
  - 摆盘建议

5. 规则校验与重排序
- 生成结果不会直接输出
- 还要校验：
  - 食材是否真实可用
  - 做法是否和厨具匹配
  - 风味是否冲突
  - 是否存在明显食安风险
  - 内容是否足够完整、合理、可执行
- 最后把候选结果中最合理的一版输出给用户

这一页最重要的口径：
- 我们的核心不是“自由生成”
- 而是“约束式生成 + 规则校验 + 候选重排序”

#### 关于“米其林三星级”的表述建议
这一页不要直接说：
- “几样简单食材生成米其林三星级成品”

建议改成：
- “让普通食材在有限条件下被重组成更高完成度、更有餐厅级表达的菜品方案”
- “通过技法、结构和风味平衡，让有限食材呈现出更高级的结果”

这样更稳，也更符合老师会接受的说法。

#### 这一页可以强调的 4 个升级逻辑
- `技法提升`：煎、烤、炖、焦化、乳化等技法提升香气和口感
- `结构重组`：从散的食材变成主体、配角、酱汁、点缀的完整结构
- `风味平衡`：控制咸、鲜、酸、甜、脂香、辛香之间的关系
- `表达升级`：通过菜名、摆盘、叙事和文案，让成品更有餐厅感

一句话收尾：
- 我们追求的不是夸张承诺“米其林三星”，而是让有限食材在约束条件下得到更高级、更完整、更可执行的表达。

---

### 第 8 页：Xcode 版本
这一页建议讲成“跨平台延展版本”。

推荐标题：
- Xcode 版本：从小程序到 App 的延展可能

建议讲法：
- 当前正式落地是微信小程序
- 但项目已经考虑过 iOS / Xcode 版本的适配可能
- 它的意义不是重复做一遍，而是说明：
  - 这套交互逻辑可以独立成立为 App
  - 这套产品体验具备迁移和延展空间
  - 海外版本可以在内容和交互上继续本地化适配

这一页不要讲太多工程细节，更适合讲：
- 同一产品逻辑如何迁移到不同端
- 为什么这个产品具备继续发展空间

---

### 第 9 页：demo 展示
这一页是实机流程展示。

推荐 demo 顺序：
- 登录进入产品
- 进入 Nexus
- 点击拍摄
- 识别并确认食材
- 进入加载过渡
- 生成结果页
- 保存到档案馆
- 从社区内容进入 Shop 导购壳

这一页的目标不是证明“页面很多”，而是证明：
- 主链路是通的
- 页面逻辑是连贯的
- 产品故事是完整的

如果时间短，demo 至少要保证两件事：
- 主链路完整跑一遍
- 社区到 Shop 的展示支线补一段

---

### 第 10 页：crossover
这一页建议作为收尾升华。

这里的 crossover 可以讲成项目的“跨界组合价值”：
- AI 识别 + 生成
- 产品设计 + 前端交互
- 饮食场景 + 健康参考
- 社区展示 + 导购入口
- H5 原型验证 + 小程序正式落地 + iOS 延展可能

这一页可以总结为：
- 《拍立食》不是一个单点功能，而是把算法、产品、设计、饮食场景和平台落地组合起来，形成一个可演示、可扩展、可继续深化的产品方案。

## 4. 推荐页序总览
如果做成 PPT，建议页序如下：

1. 封面：项目名称 + 一句话定义
2. goal：为什么要做这个产品
3. 如何形成产品：产品边界和收敛过程
4. 基本功能：主链路 + 档案馆 + 社区 + Shop
5. 广告：商业化和品牌合作延展
6. 技术页 1：整体技术架构
7. 技术页 2：约束式大模型生成
8. Xcode 版本：跨平台延展
9. demo 展示
10. crossover：总结收尾

---

## 5. 汇报时的核心口径
- 不要把当前 H5 原型讲成最终正式技术栈
- 要明确最终落地形态是微信小程序
- 不要把 Shop 讲成真实电商平台
- 不要把健康参考讲成医疗诊断
- 不要把算法讲成空泛名词，要对应到具体产品功能
- 不要把生成结果夸张成“米其林三星”，更适合讲“餐厅级表达”或“高完成度菜品方案”
